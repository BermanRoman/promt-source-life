# Локальное хранилище и очередь Google Drive

`scripts/store.py` — работающий backend на Python 3 со стандартной библиотекой, без SDK, токенов и сетевых запросов.

Канонический протокол работы с личными данными описан в [core/storage.md](../core/storage.md).

SQLite хранит канонические локальные записи и durable outbox; команды чтения создают обычные Markdown-файлы для просмотра или передачи подключённому исполнителю Drive.

Файл на Drive создаёт и читает реальный доступный connector, действующий с текущим разрешением пользователя.

Отсутствие connector оставляет запись в `local` и очередь в `pending`.

Наличие очереди не означает сохранения на Drive.

## Начало работы

Выберите приватный runtime-каталог вне Git-репозитория и каталогов общего доступа.

Путь не должен содержать симлинки, включая родительские каталоги: на macOS используйте `/private/tmp/...` вместо `/tmp/...` и `/private/var/...` вместо `/var/...`.

Ниже `PRIVATE_ROOT`, `INPUT_FILE`, `NEW_FILE`, `READBACK_FILE`, `JOB`, `REMOTE_ID` и другие значения — подставляемые пользователем пути и идентификаторы, а не готовые команды для копирования без настройки.

```sh
python3 scripts/store.py --root PRIVATE_ROOT init
python3 scripts/store.py --root PRIVATE_ROOT put --key 00-state.md --input INPUT_FILE --expected-revision 0 --operation-id setup-state-1
python3 scripts/store.py --root PRIVATE_ROOT list
python3 scripts/store.py --root PRIVATE_ROOT pending
python3 scripts/store.py --root PRIVATE_ROOT read --key 00-state.md --output NEW_FILE
```

`--root` всегда стоит перед подкомандой.

Успех возвращает JSON и код 0; отказ — код 2 и сообщение без личного текста, SQL и содержимого исключения.

`init` идемпотентен и не стирает существующие данные.

Допустимы ключи `00-справка.md`, `00-state.md`, существующая календарная дата `YYYY-MM-DD.md` и `undated-SAFE_ID.md`, где `SAFE_ID` состоит из 1–80 латинских букв, цифр, `_` и `-`.

Содержимое записи — точные UTF-8 байты: нормализации Markdown, переводов строк или Unicode нет.

Новая запись требует revision 0; последующие изменения требуют текущую revision из `list`.

Revision возрастает при локальном изменении, pull, разрешении конфликта и забывании записи.

Стабильный operation ID задаёт вызывающая сторона: допустимы 1–200 латинских букв, цифр, `_`, `-`, `.`, `:`.

Повтор `put`, `pull`, `resolve` или `forget` с тем же operation ID и аргументами возвращает прежний результат без новой записи; изменение аргументов с прежним ID отклоняется.

Operation ID должны быть уникальны для всех операций одного хранилища.

Повтор старой операции не восстанавливает забытый текст и не утверждает, что её историческая revision остаётся текущей.

`read`, `payload` и `conflict-read` создают только новый файл с правами 0600 через exclusive create, никогда не перезаписывая существующий путь.

Вывод `list` и `pending` содержит метаданные, включая названия записей и хеши, но не личный текст.

Метаданные также следует считать приватными.

## Контракт исполнителя Drive

Исполнитель получает `pending`, проверяет текущую авторизацию и sync mode, затем обрабатывает один job на ключ.

Сначала он должен иметь доступ к поиску файла по стабильному ID, чтению точных байтов, созданию/обновлению файла с сохранением стабильной метки операции и подтверждению результата.

`stable_id` из `pending` и `prepare` включает случайный постоянный ID хранилища и operation ID; его нужно записывать в доступные поиску метаданные Drive при создании файла в той же операции создания.

Идентификатор job — локальный идентификатор очереди, а `stable_id` — маркер внешней идемпотентности.

Идентичное имя Markdown-файла само по себе не доказывает идентичность записи.

Исполнитель не делится файлами и не создаёт аккаунты или токены.

1. Для обновления прочитайте remote ID из job, заново прочитайте файл и вычислите SHA-256 его точных байтов.
2. Для создания найдите файлы по `stable_id`: отсутствие должно быть проверено до первой отправки, найденный файл требует reconcile, несколько совпадений требуют остановки и ручной сверки.
3. Экспортируйте `payload --job JOB --output NEW_FILE` и сохраните байты до внешней операции в приватном месте.
4. Вызовите `prepare --job JOB --observed-sha SHA --remote-id REMOTE_ID` для обновления или `prepare --job JOB --observed-sha absent` для первого создания.
5. После успешного `prepare` выполните ровно одну внешнюю запись, сохранив её условие версии и `stable_id`.
6. Прочитайте результат обратно через connector в новый приватный файл и вызовите `ack --job JOB --remote-id REMOTE_ID --readback READBACK_FILE`.

`prepare` проверяет наблюдаемый SHA против последнего общего `base_sha` и атомарно переводит job в `writing` до сети.

Следующее `prepare` для `writing` или `unknown` запрещено.

После падения процесса `writing` тоже считается неопределённым результатом, даже если отправка могла ещё не начаться.

Connector должен поддерживать условное обновление по версии/ETag либо другой доказуемый механизм исключения внешней записи между чтением и обновлением.

Одна предварительная проверка SHA не устраняет гонку другого редактора.

Если connector не предоставляет такой гарантии, автоматическое обновление существующего файла запрещено: локальная запись сохраняется, а исполнитель сообщает о недоступной гарантии и оставляет job в очереди.

Этот CLI не подменяет условную операцию Drive локальной блокировкой и не может проверить достоверность переданного исполнителем readback без самого connector.

`ack` сравнивает readback с полными байтами queued payload, проверяет remote ID и подтверждает только конкретную revision job.

После первого успешного ack payload завершённого job удаляется; повторное подтверждение сверяется с сохранённым SHA-256, а текущие локальные байты остаются в `records`.

Если во время отправки появилась новая локальная revision, старый ack обновляет общую базу для новой очереди, но статус остаётся `local`.

Повтор старого ack после подтверждения более новой revision не откатывает общую базу.

## Неопределённый результат

```sh
python3 scripts/store.py --root PRIVATE_ROOT unknown --job JOB
python3 scripts/store.py --root PRIVATE_ROOT reconcile --job JOB --remote-id REMOTE_ID --readback READBACK_FILE
```

При таймауте, потере ответа или падении после `prepare` исполнитель не повторяет create или update вслепую.

Он ищет результат по `stable_id` в метаданных Drive, проверяет remote ID для обновления и читает реальные байты.

Точное совпадение допускает `reconcile`, использующий те же проверки, что `ack`.

Несовпадение нужно сохранить как конфликт.

Если поиск не находит результат, CLI намеренно не возвращает `unknown` в `pending`: отрицательный поиск не доказывает, что отложенная операция ещё не завершится.

Без найденного результата или доказуемой внешней идемпотентности операция остаётся `unknown` до предметного восстановления исполнителем; автоматического повторного создания нет.

Нельзя создавать новый локальный job ради обхода неопределённого результата предыдущего job того же ключа.

## Конфликт и pull

При отличии actual remote SHA от `base_sha` и наличии локальной очереди не перезаписывайте Drive.

```sh
python3 scripts/store.py --root PRIVATE_ROOT conflict --job JOB --remote-id REMOTE_ID --readback READBACK_FILE
python3 scripts/store.py --root PRIVATE_ROOT conflict-read --job JOB --output NEW_FILE
python3 scripts/store.py --root PRIVATE_ROOT resolve --job JOB --input REVIEWED_MERGE_FILE --expected-revision N --operation-id merge-1
```

`conflict` сохраняет удалённые байты отдельно, оставляя локальные запись и queued payload доступными.

Повтор той же пары байтов и remote ID допустим; замена уже сохранённого конфликта другой remote version отклоняется, чтобы не потерять первую версию.

Для нескольких внешних версий сначала экспортируйте сохранённый конфликт и выполните предметную сверку.

`resolve` принимает явно проверенный результат слияния, CAS текущей локальной revision и создаёт новую очередь с remote SHA конфликта как общей базой.

Если remote снова изменился после сверки, следующий `prepare` снова отклонит отправку.

Решение «оставить моё» или «принять удалённое» также требует явно выбранного файла в `resolve`; автоматического last-write-wins нет.

Если локальных pending, writing, unknown или conflict jobs нет, прочитанное удалённое изменение можно принять через CAS:

```sh
python3 scripts/store.py --root PRIVATE_ROOT pull --key 2026-11-06.md --input READBACK_FILE --expected-revision N --remote-id REMOTE_ID --operation-id pull-1
```

`pull` также допускает первое чтение ранее неизвестной записи с revision 0, если исполнитель подтвердил принадлежность remote файла нужному пользователю и ключу.

Забытый ключ не восстанавливается ни через `pull`, ни через `put`.

## Пауза, отзыв и забывание

```sh
python3 scripts/store.py --root PRIVATE_ROOT sync paused
python3 scripts/store.py --root PRIVATE_ROOT sync revoked
python3 scripts/store.py --root PRIVATE_ROOT sync enabled
python3 scripts/store.py --root PRIVATE_ROOT forget --key 2026-11-06.md --expected-revision N --operation-id forget-1
```

`paused` и `revoked` запрещают новые `prepare`, сохраняя локальные изменения и очередь.

`revoked` фиксирует отзыв синхронизации; сам connector и его разрешения пользователь отключает в соответствующем приложении.

Возобновление после отзыва требует нового текущего разрешения пользователя; исполнитель не вызывает `sync enabled` самостоятельно.

Уже отправленную внешнюю операцию локальный флаг отозвать не может, поэтому её результат всё равно нужно сверить через readback.

`forget` атомарно удаляет текст записи, все её payload в outbox и сохранённые удалённые конфликты, включая историю, и оставляет durable tombstone и job удаления Drive.

Ключ, revision, технические ID и хеши аргументов идемпотентности остаются для предотвращения повторов и воскрешения данных.

Удаление локального текста не объявляет удалённый файл удалённым.

Если ранее был неопределённый create, deletion job сохраняет `target_operation_id` и `target_stable_id` для поиска результата перед удалением.

Переход неопределённого create в conflict сохраняет эту обязанность: перед очисткой backend собирает remote ID из записи, активных jobs и всех retained conflicts.

Если найдены разные remote ID, `forget` возвращает отдельные deletion jobs в массиве `jobs`, сохраняя поле `job` как первый элемент для совместимости.

Каждую копию нужно проверить и подтвердить отдельно; подтверждение одной оставляет статус `deletion-pending`, пока есть другие незавершённые цели.

`stable_id` deletion job дополнительно включает его job ID, чтобы разные удаления одного поручения не имели общего внешнего ключа идемпотентности.

Для известного remote ID подтверждение без ID или с другим ID отклоняется даже после удаления локального текста и conflicts.

Исполнитель находит соответствующий файл, выполняет удаление по remote ID и подтверждает отсутствие через connector:

```sh
python3 scripts/store.py --root PRIVATE_ROOT prepare --job DELETE_JOB --observed-sha SHA --remote-id REMOTE_ID
python3 scripts/store.py --root PRIVATE_ROOT ack-delete --job DELETE_JOB --remote-id REMOTE_ID --confirmed-absent
```

Для удаления `observed-sha` служит свидетельством свежего чтения, но совпадения с прежней общей базой не требуется: поручение касается всей записи.

Удалять по имени без доказанной принадлежности файла нельзя.

Если запись никогда не отправлялась и connector подтвердил отсутствие по стабильным ID относящихся к ней операций, допустим `ack-delete --job DELETE_JOB --confirmed-absent` без remote ID.

Для неопределённого create подтверждение без найденного remote ID запрещено: отрицательного поиска недостаточно для исключения запоздалого создания.

Внешнее удаление здесь означает подтверждённое отсутствие активного файла, а не гарантированное физическое стирание резервных копий, истории версий или корзины провайдера.

Исполнитель обязан объяснить пользователю фактическую семантику использованного delete/trash инструмента.

CLI не выполняет тематическое вымарывание по всем записям и не стирает экспортированные Markdown-файлы, исходные input/readback, резервные копии, снимки файловой системы и память внешних приложений.

Забывание ограничено одной записью в канонической SQLite и её retained history/outbox/conflicts.

`secure_delete=ON`, DELETE journal и последующий VACUUM очищают текст из текущего файла БД, но не дают обещания физического стирания с SSD или снапшотов.

## Состояния и устройство

| Статус записи | Значение |
| --- | --- |
| `local` | Локальные байты сохранены, актуальная revision на Drive не подтверждена. |
| `both` | Точные байты текущей revision проверены последним readback Drive. |
| `unknown` | Есть отправляемая операция `writing` либо неизвестный результат `unknown`. |
| `conflict` | Сохранены локальные данные и несовместимая удалённая версия. |
| `deletion-pending` | Локальный текст забыт, удаление Drive ещё не подтверждено. |
| `deleted` | Есть tombstone и подтверждение отсутствия активного remote файла. |

`both` описывает последнюю проверенную общую revision, а не непрерывный мониторинг последующих внешних изменений.

Таблицы: `records` — текущая запись, revision, SHA, remote ID, last shared SHA/revision и tombstone; `jobs` — queued bytes и автомат состояний; `operations` — отпечатки аргументов и результаты идемпотентности; `conflicts` — сохранённые remote bytes; `settings` — sync mode и store ID.

SQLite `BEGIN IMMEDIATE`, FULL synchronous и rollback journal обеспечивают один атомарный коммит данных и очереди и CAS между локальными процессами.

Права runtime-каталога — 0700, БД — 0600; ссылки, traversal и runtime внутри этого репозитория отклоняются.

Это защита от случайного раскрытия файлов, а не от процесса с правами того же пользователя, подменяющего каталоги во время операции.

БД не зашифрована; используйте приватный зашифрованный диск и не кладите runtime в Git или общий sync-каталог.

Backend не запускает фоновых процессов и сам не возобновляет сетевую работу.

Проверка без сети и аккаунта:

```sh
python3 -m unittest discover -s tests -p test_store.py -v
```
